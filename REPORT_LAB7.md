# Лабораторна робота №7
## Реалізація політики контролю доступу в клієнт-серверній системі

**Дисципліна:** захист інформації / контроль доступу  
**Студентка:** Тетяна  
**Варіант:** 3 — модель Белла–ЛаПадули з категоріями  
**База:** програмний комплекс лабораторної роботи №6 (токен, SHA-256, TCP, loopback)

---

### 1. Мета роботи

Ознайомитися з мандатним контролем доступу, реалізувати одну з класичних політик на базі клієнт-серверної програми ЛР6 і дослідити дозволи та відмови для кількох користувачів і набору об’єктів даних.

### 2. Завдання

1. На основі програми ЛР6 розробити клієнт, який працює з об’єктами (текстові файли / рядки) на сервері.
2. Реалізувати політику доступу за варіантом. Кількість прав — не менше чотирьох, включно з правом власника.
3. Відлагодити систему на інтерфейсі loopback (`127.0.0.1`), далі передбачити роботу в реальній мережі лабораторії.
4. Запротоколювати роботу щонайменше для трьох користувачів і десяти об’єктів.
5. Оформити звіт.

### 3. Обраний варіант і обґрунтування

Обрано **варіант 3 — модель Белла–ЛаПадули (Bell–LaPadula) з категоріями**.

Чому саме вона:

- продовжує ЛР6: спочатку автентифікація токеном, потім **авторизація** за мандатною міткою;
- добре демонструє конфіденційність (заборона витоку секретів «вниз»);
- категорії (`need-to-know`) дають відмови навіть на однаковому рівні секретності;
- право власника (`OWN`) додається як окреме дискреційне право (створення / видалення свого об’єкта), щоб виконати вимогу «не менше 4 прав, враховуючи право власника».

### 4. Теоретичні відомості

Кожному суб’єкту (користувачу) і об’єкту (файлу) призначається **мітка безпеки**:

- рівень секретності (гратка):  
  `UNCLASSIFIED (0) < CONFIDENTIAL (1) < SECRET (2) < TOP_SECRET (3)`;
- множина категорій: `{Фінанси, Кадри, Техніка}`.

**Домінування.** Мітка `(L_h, C_h)` домінує над `(L_l, C_l)`, якщо  
`L_h ≥ L_l` і `C_l ⊆ C_h`.

**ss-властивість (simple security, no read-up):** читати можна, лише якщо суб’єкт домінує над об’єктом. Не можна читати документи вищого рівня або чужої категорії.

**★-властивість (star property, no write-down):** писати / дописувати можна, лише якщо об’єкт домінує над суб’єктом. Не можна «злити» секрет у файл нижчого рівня і не можна розширити коло категорій записом.

**Право власника (`OWN`):** видаляти об’єкт може лише той, хто його створив (або кому він призначений власником). Навіть `admin` з міткою TOP_SECRET не видаляє чужі файли — це окреме право, не виведене з рівнів BLP.

Реалізовані права (4):

| Право | Призначення | Правило |
| --- | --- | --- |
| OWN | створення, видалення | ім’я суб’єкта = власник |
| READ | читання вмісту | ss-властивість |
| WRITE | повний перезапис | ★-властивість |
| APPEND | дописування | ★-властивість |

### 5. Архітектура програми

Система ЛР6 збережена і розширена.

1. `create_token.py` / `lab7_create_tokens.py` — XOR-захист файлу `security_token.dat` (ім’я + SHA-256 пароля).
2. Клієнт зчитує токен, дешифрує XOR-ключем `0xAA`, надсилає JSON на TCP-порт `9099`.
3. Сервер звіряє хеш із `USERS_DB`. Після успіху сеанс **не закривається**: клієнт працює з об’єктами командами `LIST`, `READ`, `WRITE`, `APPEND`, `CREATE`, `DELETE`, `PROFILE`, `QUIT`.
4. Модуль `lab7_access.py` приймає рішення доступу; сервер пише журнал `protocol_lab7.log`.

Файли проєкту ЛР7:

- `lab7_access.py` — правила Белла–ЛаПадули;
- `lab7_server.py` — сервер, сховище `server_objects/`;
- `lab7_client.py` — інтерактивний клієнт;
- `lab7_create_tokens.py` — токени трьох користувачів;
- `lab7_demo.py` — автоматичний протокол;
- `tokens/admin`, `tokens/Tetyana`, `tokens/student`.

### 7. Хід роботи (як запустити)

Loopback (відлагодження):

```text
python lab7_create_tokens.py
python lab7_server.py
```

У другому вікні:

```text
python lab7_client.py tokens\student
python lab7_client.py tokens\Tetyana
python lab7_client.py tokens\admin
```

Автоматичний протокол трьох сеансів:

```text
python lab7_demo.py
```

Реальна мережа лабораторії:

- на сервері: `LAB7_HOST=0.0.0.0` (слухати всі інтерфейси);
- на клієнті: `LAB7_HOST=<IP-адреса сервера>`;
- брандмауер повинен пропускати TCP `9099`.

Скидання сховища об’єктів: видалити каталог `server_objects` і перезапустити сервер.

### 8. Протокол експерименту (loopback 127.0.0.1:9099)

Нижче — фактичний вивід `lab7_demo.py` (три користувачі, 12 об’єктів). Пояснення рішень — у розділі 9.

```text
===== Сеанс користувача student =====
AUTH SUCCESS. Мітка: CONFIDENTIAL | Техніка
LIST: 12 об'єктів
READ public_notice.txt -> OK
READ lab_guide.txt -> OK
READ grades.txt -> DENIED   (категорія «Кадри» відсутня у student)
READ strategy.txt -> DENIED (no read-up: TOP_SECRET)
WRITE lab_guide.txt -> OK   (той самий рівень і категорія «Техніка»)
WRITE public_notice.txt -> DENIED (no write-down)
APPEND equipment.txt -> OK
CREATE student_notes.txt -> OK (OWN)
DELETE budget_2026.txt -> DENIED (не власник)
DELETE student_notes.txt -> OK (OWN)

===== Сеанс користувача Tetyana =====
AUTH SUCCESS. Мітка: SECRET | Фінанси, Кадри
READ budget_2026.txt -> OK
READ grades.txt -> OK
READ incident_plan.txt -> DENIED (no read-up / неповні категорії)
READ lab_guide.txt -> DENIED (категорія «Техніка» не входить до мітки Tetyana)
WRITE budget_2026.txt -> DENIED
  (у Tetyana є зайва категорія «Кадри» відносно об'єкта {Фінанси}:
   запис розширив би need-to-know)
WRITE public_notice.txt -> DENIED (no write-down)
APPEND staff_salaries.txt -> OK
  (SECRET і {Кадри, Фінанси} точно покривають мітку Tetyana)
DELETE grades.txt -> OK (власник)
CREATE hr_memo.txt -> OK (OWN)

===== Сеанс користувача admin =====
AUTH SUCCESS. Мітка: TOP_SECRET | усі категорії
READ incident_plan.txt -> OK
READ staff_salaries.txt -> OK
READ public_notice.txt -> OK   (читання вниз дозволене)
WRITE public_notice.txt -> DENIED (no write-down)
WRITE strategy.txt -> DENIED
  (категорії admin ширші за {Фінанси})
WRITE ts_full.txt -> OK
  (об'єкт має повний набір категорій і рівень TOP_SECRET)
APPEND crypto_notes.txt -> DENIED (рівень SECRET < TOP_SECRET)
CREATE admin_ts.txt -> OK
DELETE admin_ts.txt -> OK (власник)
DELETE hr_memo.txt -> DENIED (не власник, попри TOP_SECRET)
```

Повний машинний журнал сервера збережено у файлах `protocol_demo.txt` та `protocol_lab7.log`.

### 9. Аналіз результатів

1. **Конфіденційність працює.** `student` не читає `strategy.txt` (вищий рівень) і не читає `grades.txt` (чужа категорія «Кадри» при однаковому CONFIDENTIAL).
2. **Витік вниз блокується.** Ні `student`, ні `Tetyana`, ні навіть `admin` не можуть писати в `public_notice.txt` (UNCLASSIFIED): це класична ★-властивість.
3. **Запис «вгору» дозволений.** `student` може `WRITE`/`APPEND` технічні файли не нижчого рівня (`lab_guide.txt`, `equipment.txt`, навіть `crypto_notes.txt` і `ts_full.txt` за категорією «Техніка»). Секрет при цьому не знижується.
4. **Категорії — не декорація.** `Tetyana` читає `budget_2026.txt` (`{Фінанси} ⊆ {Фінанси, Кадри}`), але не може його перезаписати, бо її категорії не є підмножиною категорій файлу. Натомість `staff_salaries.txt` з обома категоріями дозволяє їй APPEND.
5. **Високий рівень ≠ всевладність.** `admin` читає все, але пише лише в об’єкти, що домінують над його повною міткою (`ts_full.txt`). Чужий `hr_memo.txt` він не видаляє — спрацьовує право власника.
6. **Не менше чотирьох прав** спостерігаються в одному сеансі, наприклад у `student` для `equipment.txt`: `OWN, READ, WRITE, APPEND`.

### 10. Висновки

1. Програму ЛР6 розширено до повноцінної роботи клієнта з текстовими об’єктами на сервері після автентифікації токеном.
2. Реалізовано мандатну політику **Белла–ЛаПадули з категоріями (варіант 3)** і чотири права: **OWN, READ, WRITE, APPEND**.
3. Відлагодження виконано на **loopback 127.0.0.1:9099**. Для комп’ютерної лабораторії достатньо змінити `LAB7_HOST` і відкрити порт.
4. Протокол зібрано для **трьох користувачів** (`student`, `Tetyana`, `admin`) і **дванадцяти об’єктів**. Зафіксовано як дозволи, так і відмови, що підтверджує коректність ss-властивості, ★-властивості та права власника.
5. Модель захищає конфіденційність, але ускладнює запис для суб’єктів із широкими категоріями; на практиці її часто поєднують з дискреційними правами (як зроблено для `OWN`).

### 11. Відповіді, які можна вставити в захист

**Чим ЛР7 відрізняється від ЛР6?**  
ЛР6 відповідає на питання «хто ти?» (автентифікація). ЛР7 — «що тобі можна?» (авторизація / MAC).

**Чому admin не може змінити оголошення?**  
Запис у UNCLASSIFIED з TOP_SECRET — це write-down, заборонений моделі, яка захищає саме конфіденційність.

**Навіщо категорії, якщо вже є рівні?**  
Щоб розділяти «потрібно знати»: фінансист із SECRET не читає технічну методичку, навіть якщо її рівень нижчий, бо категорія «Техніка» не входить до його мітки.

**Чому право власника окреме?**  
BLP не описує видалення файлів. Власник — дискреційне право, якого вимагає завдання (≥ 4 права).
